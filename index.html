openai says my FIDO2 hardware key is a passkey

I built a physical ESP32-C3 FIDO2 key. Chrome registers it. OpenAI accepts it. Daybreak still files it under Passkey. apparently the missing feature is corporate paperwork.

September 28, 2026 ESP32-C3 / Pico FIDO2 6.6 CTAP 2.1 / FIDO2 / U2F

this started because Daybreak wants physical FIDO2 hardware keys and i had the obvious thought: fine, i'll build one.

I already had an ESP32-C3. Pico FIDO2 runs on it. it speaks USB HID, CTAP 2.1, FIDO2, U2F, supports a client PIN, resident credentials, the usual stuff.

so i flashed it, fought with Linux for a while, and eventually got exactly what i wanted: a tiny physical security key that Chrome can talk to.

then OpenAI accepted the credential and called it a Passkey.

not "security key." not "hardware key." Passkey.

which is a problem because Daybreak explicitly cares about that distinction.

first, udev wasted a chunk of my afternoon for no reason

before getting to the interesting problem, the key looked completely dead in Chromium.

/dev/hidraw8 kept coming back as:

0600 root:root

I had a sane rule:

SUBSYSTEM=="hidraw", ATTRS{idVendor}=="feff", ATTRS{idProduct}=="fcfd", GROUP="plugdev", MODE="0660", TAG+="uaccess"

udevadm test happily told me the rule worked.

replug the key: still root only.

rewrite rule. reload rule. stare at rule. threaten rule. still root only.

eventually i checked whether udevd was actually doing its fucking job.

pid 611  udevd   ELAPSED 17-08:49   CPU TIME 1-23:59:58   11.5%   1 thread

it had burned almost two days of CPU time in a single-thread spin loop and was processing no events.

KERNEL remove  .../hidraw8
KERNEL add     .../hidraw8

# no UDEV event. nothing. daemon is just sitting there eating a core.

restart udevd:

sudo sv restart /var/service/udevd

and suddenly:

/dev/hidraw8 660 root:plugdev
/dev/hidraw9 660 root:plugdev

fine. annoying, but solved.

also a useful reminder that udevadm test is a simulation. it can tell you the rules on disk are perfect while the real daemon is face-down in a ditch.

that last line is the whole problem.

openai's docs are why i think this is worth complaining about

the general Advanced Account Security documentation says:

You can use any FIDO-compatible security key with Advanced Account Security.

it explicitly lists a passkey plus a hardware key, or two hardware security keys, as valid setups.

Daybreak is stricter. the Daybreak overview requires physical FIDO2 hardware security keys and says software or synced passkeys do not qualify.

fine. i actually agree with the basic idea there. if you are handing out access to a security research model, requiring hardware-backed login is not some insane request.

but then we get to this:

physical:                     yes
USB HID authenticator:       yes
CTAP 2.1:                    yes
FIDO2 registration:          works
FIDO2 authentication:        works
credential lives on ESP32:   yes
OpenAI says hardware key:    no
OpenAI says Passkey:         yes

and now i want to know what the actual requirement is.

because "physical FIDO2 hardware security key" and "hardware authenticator whose vendor identity our backend recognizes" are not the same sentence.

the AAGUID is the suspicious part

Pico FIDO2 reports:

89fb94b7-06c9-3673-9b7e-30526d968145

that is not some Yubico or Feitian model identifier. the firmware project assigned it itself. in the source it is literally derived from the first 16 bytes of SHA256("Pico FIDO2").

it is also not represented in the FIDO Metadata Service as a recognized commercial authenticator model.

and the firmware does self-attestation. there is no manufacturer attestation certificate chain that lets a relying party walk backwards from this credential to "yes, Yubico manufactured model X" or whatever.

that leaves OpenAI with a perfectly functional FIDO2 credential and very little vendor provenance.

my current theory is that this is why it falls into the generic Passkey bucket.

theory. not fact.

I do not have OpenAI's credential-classification code. they could be looking at MDS, attestation, browser hints, some internal allowlist, or a cursed pile of all four.

what i can observe is that the key works, has a self-assigned AAGUID, self-attests, and OpenAI refuses to type it as a hardware security key.

that is enough to ask the question. it is not enough to pretend i reverse engineered their backend.

attestation is where this starts to piss me off

attestation itself is not evil. it has a real purpose.

if i run a company and my security policy says "employees may only use these approved authenticator models," attestation gives me a way to enforce that instead of taking the browser's word for it.

it can tell a relying party what kind of authenticator created a credential and give it a chain of trust back to whoever manufactured that authenticator.

cool.

what it does not do is magically define whether a thing is physical hardware.

there is an ESP32-C3 in my hand.

the fact that nobody sold it to me in a blister pack does not turn it into Google Password Manager.

the lack of a vendor certificate also does not, by itself, prove that the private credential key left the device, or that WebAuthn suddenly stopped being phishing resistant.

what is missing is provenance.

and if provenance is your actual security requirement, say provenance.

this is the part of the attestation ecosystem i dislike: the protocol can be open, the implementation can be open source, i can build a device that interoperates correctly, and i can still become second-class hardware because i am not an established authenticator vendor with metadata and certificate infrastructure behind me.

that is an extremely convenient setup for established manufacturers.

it is considerably less convenient for open hardware, weird hardware, research hardware, and the guy with an ESP32 and a soldering iron.

there are legitimate reasons for a relying party to want certified or specifically approved authenticators. supply-chain assurance is real. implementation quality matters. a homemade authenticator can absolutely contain security bugs that a mature commercial product does not.

but then the policy should be:

we require an approved / attestable authenticator model

not:

we require a physical FIDO2 hardware security key

those are different requirements.

using attestation as a hidden definition of "hardware" is shitty security policy because nobody can tell what property you are actually enforcing. is the goal hardware-backed key storage? a certified implementation? a known manufacturer? an approved supply chain? a device model on an allowlist?

pick one. document it.

no, i am not going to make it pretend to be a yubikey

there is an obvious dumb direction this could go.

patch the firmware with the AAGUID of a known commercial authenticator.

i am not doing that.

first, that would be lying about the device.

second, if OpenAI is actually validating attestation, spoofing an AAGUID gets me nowhere because i do not have the manufacturer's attestation key or certificate chain.

third, "make my DIY security key work by impersonating somebody else's security key" is a pretty spectacular way to miss the point.

I want it accepted as what it is:

a physical, self-built, standards-compatible FIDO2 authenticator

if that class of device is not allowed, fine. just tell me that.

the october 1 deadline makes this less academic

the current Daybreak docs say existing individual users have until October 1, 2026 to meet the account-security requirements.

I found this on September 28.

excellent.

the Daybreak troubleshooting page actually says to contact Support if a compatible physical key is not recognized, so that is what i did.

at this point i want one of two answers:

1. this should count as a physical FIDO2 key and the classification is wrong

or

2. Daybreak requires a recognized / attestable / approved authenticator model

either answer is useful.

if the answer is "buy a commercial key," whatever. that costs money and annoys me, but at least it is actionable.

the useless answer is documentation that says "compatible FIDO2 hardware key" while the implementation silently requires some other property.

what i sent support

I did not send them "please make my weird ESP32 work."

the actual complaint is the mismatch:

Your documentation says Daybreak requires a compatible physical FIDO2 hardware security key. My physical ESP32-C3 authenticator implements FIDO2/CTAP2.1 and successfully registers and authenticates with ChatGPT, but ChatGPT classifies the credential as a passkey rather than a hardware security key. The authenticator has a self-assigned AAGUID and self-attestation rather than a vendor identity represented in FIDO metadata. If Daybreak actually requires an attested or metadata-recognized authenticator, please document that requirement. If it does not, this appears to be an interoperability problem in credential classification.

that is the question.

not whether OpenAI owes me support for every microcontroller i can make enumerate as HID.

whether the documented security property and the enforced security property are actually the same thing.
